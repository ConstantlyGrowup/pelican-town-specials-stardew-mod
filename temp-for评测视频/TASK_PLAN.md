## 1. 演示目标

用本项目的菜品原料映射场景，展示 JEV 如何以固定选项完成批量文本评测：读取菜名、现实原料和待评估的游戏原料，选择「合理 / 不合理 / 无法判断」，系统自动与提前固定的 Ground Truth 比较。观众点击开始后，看见请求并发完成、结果逐条出现，最后得到判断准确率、总耗时和费用。

主要验证对象是 **JEV 这个评测器**，因此本次准确率定义为「JEV 的判断与参考答案一致的比例」。之前 RAG 的 Gold 命中率、JEV 判为合理的比例均不能直接当成本次 JEV 准确率。

希望验证的是“批量评测是否足够准确、快速、便宜”；视频结论由实测数字决定，不预填高准确率或承诺速度优势。并发是客户端调度能力，观测耗时包含网络与服务端响应。

## 3. 数据与 Ground Truth 设计

### 3.1 建议主集：720 条判定题

基于 120 道菜中的 360 项现实原料，每项构成两个候选对应关系，建议形成 360 条「合理」和 360 条「不合理」。页面明确写“120 道菜 · 360 项原料 · 720 条判断题”，不把数量解释成 720 个不同菜品。

| 样本 | 构建方法 | 参考答案 | 用途 |
|---|---|---|---|
| 正例 | 从该项已标注的可接受 ID 中，按固定规则选一个对应物 | 合理 | 检验正确匹配是否被误拒 |
| 负例 | 优先采用已有旧链路的真实误配候选；不足部分按固定规则构造错误对应 | 不合理 | 检验错误匹配是否被放过 |
| 歧义候选 | 标签范围不完整、类别替代或翻译造成多解 | 先核对；无法明确的留在歧义附表 | 避免把标签缺陷当模型错误 |

关键规则：

1. `acceptable_item_ids` 是正例依据；**不在 Gold 集合中不自动代表不合理**。负例必须确认在同一语义评判规则下确实错误，不能只做 ID 不等判断。
2. 负例兼顾明显不相关、相近名称混淆、原料与成品混淆。难度分类和数量在运行前公布；不能根据 JEV 答案删掉困难样本。
3. 候选正负标签的核对是建立评测参考答案，JEV 仍承担正式全量判定。所有负例记录可审查的标签依据和来源，完成标签核对后才能把结果称作准确率。
4. 对游戏物品 `246` 的规则预先固定：英文 `Wheat Flour` 为语义真源，中文游戏显示名仍保留“大麦粉”。把此通用目录翻译约定写入评判规则，两类样本一视同仁；不对本轮结果事后改判。
5. 构造的是“现实原料与游戏候选是否对应”的题，不混入运行时 fallback 状态或 API 失败当语义负例。
6. 正负题交错，用固定随机种子打乱；两条速度对照链路使用完全相同的题和顺序。重复的完整判定输入要识别、记录，数据规模同时报告唯一输入数量，不能靠复制请求制造知识覆盖量。
7. 冻结 `cases.jsonl`、标签、目录摘要、rubric、顺序与 SHA-256。配对的正负例同属一项原料，统计不是 720 个独立菜品样本。
8. 若标签核对后不能凑齐 720 条明确样本，按实际冻结数量展示；规划数量不能覆盖数据质量要求。

示例仅说明格式，尚未作为正式冻结样本：

| 菜品 | 现实原料 | 待评估的游戏原料 | 参考答案 | 标签依据 |
|---|---|---|---|---|
| 樱桃番茄蘑菇煎蛋 | cherry tomatoes | Tomato / 西红柿 | 合理 | 原 Gold 包含番茄对应物 |
| 樱桃番茄蘑菇煎蛋 | cherry tomatoes | Cherry / 樱桃 | 不合理 | 食材身份不同，不能因名字重叠而对应 |
| 蓝莓松饼 | wheat flour | Wheat Flour / 大麦粉 | 合理 | 已确认的游戏翻译约定 |

### 3.2 发送给 JEV 的内容

仅包括：菜名、现实原料、当前待评估候选的游戏 ID/中英文名，以及一致的评判规则。返回三选一：`reasonable`、`unreasonable`、`undecidable`。

参考答案、Gold ID 集合、标签依据、正负类别、旧/新链路标签、检索分数均留在本地评分侧。网页可以显示参考答案，但服务端构造请求必须使用字段白名单，不能把整行网页数据直接发送。

JEV 返回选项与接口实际提供的置信度。置信度不等同于正确率；网页中的标签依据来自预先标注，不显示成“JEV 的思考理由”。

## 4. 时间与费用实验

建议同一冻结集合分别运行 **并发 1** 和 **并发 8**，各一次。串行基线可在录制前运行并保存，视频现场点击开始运行并发 8；最终用两次真实记录对照。

| 项目 | 记录方式 |
|---|---|
| 整批耗时 | 服务端单调时钟：开始执行至全部请求进入终态；包含排队、限流等待和超时 |
| 单项响应时间 | 从发起该项请求到取得响应或失败；展示 P50/P95，和排队时间分开 |
| 有效吞吐 | 有效 typed choice 数 / 整批耗时，单位条/秒 |
| 并发加速比 | 同集串行整批耗时 / 并发整批耗时；同时列出两轮完成率和准确率 |
| 费用 | 累计服务商响应中的实际 `usage.cost`；列出 USD 和“已获得费用字段的请求数/已发送数” |
| 总实验费用 | 两轮及协议探针分别计费、分别展示，再求合计；不会只报便宜的一轮 |

两轮使用相同模型、rubric、客户端机器、超时和重试策略；尽量连续运行，记录时间段和实际返回模型版本。固定 seed 只固定题目顺序，不保证远端模型确定性。单次对照仅支持“本次运行”的提速结论，不能宣称稳定服务 SLA。

建议每题只发一次、单次超时 45 秒，不自动重试；失败留在固定分母。这样名义上限为 `720 × 2 + 最多 2 个协议探针 = 1442` 次请求。实际规模、接口能力与预算在实施预检时固定，本次规划没有发起请求。重复点击开始不产生新 run；额外重新评测须显式开启新一轮。

若服务商限流，记录 429 和实际并发，不把限流等待删出耗时。费用字段缺失显示“费用不完整”，未知不写成 0；基于价格表的推算只能单独标为估算。模型版本不一致时仍展示各轮结果，但不把差异全部归因为并发。

真实速度实验关闭本地结果复用。录制辅助可提供“回放已完成记录”，必须在界面标为回放；回放不计作新实测，也不产生 API 请求。

## 5. 网页：录屏可读性优先

### 5.1 首屏布局

推荐浅色背景、深色文字、蓝色主按钮，兼容 1920×1080 录屏和 1280×720 回看。页面主体为表格，默认每页 8 行，避免几十行小字和持续滚动。标题 28–32px，主要数字 32–40px，表格正文 16–18px；数字等宽，列宽固定。

```text

120 道菜 · 360 项原料 · 720 条判断题        并发 8 · 实时运行

[完成 0/720]   [已用 00:00.0]   [判断准确率 —]   [累计费用 $—]
────────────────── 进度条 ──────────────────────────────
```

运行中的准确率标为“已完成部分”，并显示当前计分分母；结束后切换为固定全集最终指标。尚未运行时显示“—”，不显示 100%。

### 5.2 表格列的含义

| 列 | 展示 | 可读性与解释规则 |
|---|---|---|
| 菜品 | 中文名为主 | 长名最多两行，展开可见英文和 case ID |
| 现实原料 | 保留原 query，配本地核对过的中文辅助名 | 观众能直接理解要对应什么 |
| 游戏原料 | 中文展示名 + 英文名 | 翻译冲突时英文常显；详情给游戏 ID |
| 参考答案 | 合理 / 不合理 | 标题可点击了解 Ground Truth 来源 |
| JEV 判断 | 等待 / 处理中 / 合理 / 不合理 / 无法判断 / 请求失败 | “不合理”是合法答案，不能直接染成错误红色 |
| 是否判对 | ✓ 一致 / × 不一致 / — 待完成或失败 | 正确选出“不合理”同样显示绿色一致；颜色辅以文字和图标 |
| 耗时 | 例如 0.42 s | 单项请求耗时，排队时间放详情；此处数字仅为格式示例 |

行详情展示“评判输入”“参考标签依据”“JEV 原始选项与可用置信度”，三者分区。没有 JEV 生成的理由栏。

表格默认使用冻结顺序，状态变化不导致跳行；不自动切页、不自动滚屏。可另设“跟随最新完成”开关，默认关闭。进度汇总即时更新，表格批量合并更新，减少闪烁。不一致项提供单击筛选，但最终分母始终是整批样本。

### 5.3 页面状态

| 状态 | 页面表现 |
|---|---|
| 待开始 | 展示样本量、正负分布、并发、模型、预计请求上限、费用估算及开始按钮 |
| 运行中 | 开始按钮禁用；显示服务端时间、完成数和每行状态；允许停止继续派发 |
| 正在停止 | 不再创建请求，已发送请求继续结算时间与费用 |
| 已停止 | 显示部分完成数据，标明未完成；不能显示完整评测成功 |
| 完成 | 冻结总计时，展开最终总结；失败、无法判断仍可见 |
| 回放 | 明显标注回放和原 run 时间；播放耗时与原始评测耗时分开 |

浏览器刷新后重新连接同一 run，服务端返回完整快照，不重复付费。凭证缺失时开始按钮禁用并提示本地配置，不把 Key 放入前端。

## 6. 最终结果页与指标

最上方一句话模板：

> JEV 完成了 N 条原料对应判断，总耗时 T 秒，已报告费用为 $C；其中 K 条与预先固定的参考答案一致，全集判断准确率为 K/N。

| 指标 | 定义 | 展示位置 |
|---|---|---|
| 全集判断准确率（主指标） | 判断正确条数 / 全部冻结题数；无法判断、请求失败和无效响应不算正确 | 首屏大卡片，带分子/分母 |
| 有效回答准确率 | 判断正确条数 / 合理或不合理的有效回答数 | 详情，必须同时显示覆盖率 |
| 明确回答覆盖率 | 合理或不合理的有效回答数 / 全部题数 | 总结区 |
| 正例识别率 | 正例中选合理的数量 / 全部正例数 | 混淆矩阵旁 |
| 负例识别率 | 负例中选不合理的数量 / 全部负例数 | 混淆矩阵旁，突出识错能力 |
| 均衡准确率 | 正例识别率与负例识别率的平均值 | 详情，避免类别失衡误导 |
| 全选“合理”的参考分数 | 正例数 / 全部题数 | 详情，说明为什么需要负例 |
| 时间、吞吐、费用 | 按第 4 节口径 | 总结大卡片与串行/并发表 |

混淆表按 Ground Truth 正/负两行，JEV 合理/不合理/无法判断/失败四列展示；所有单元格加总必须等于 N。视频以单项判断正确率为主，不沿用之前“整道菜三项都合理”的产品指标。

结果同时列出数据和规则版本、实际模型版本、运行时间、标签来源、难度分布与不一致样例。由于本集为基于项目 Gold 构造的均衡诊断集，结论适用于本批样本，不直接换算成真实用户流量的效果。

## 7. 轻量实现与目录约束

独立 Python 本地服务（优先复用现有环境的 FastAPI / HTTP 客户端）＋静态 HTML/CSS/JS。服务端有限并发请求，SSE 传递进度；不需要新前端框架、数据库或生产路由。绑定 `127.0.0.1`，API Key 仅从本地环境变量读取。

所有新增代码、数据快照、计划、运行日志与导出放在本目录；读取项目 fixture 和目录后在本目录生成带来源哈希的快照。建议结构：

## 9. 视频建议顺序

1. 用一条番茄/樱桃案例介绍问题和参考答案，说明 JEV 只需选择，不必输出长文本。
2. 展示 120 菜/360 原料/720 判断题和正负分布，点击开始并发评测。
3. 看计时和完成数上升，展开一条正确识别“不合理”的记录，解释两列的区别。
4. 结束后展示准确率、正负例识别率、耗时、费用，再与已记录的串行结果比较。
5. 展示实际不一致项或无法判断项，说明这类工具适合快速批量筛查，争议项可以集中复核。
