# 原料对应改进｜原始匹配 vs 完整 RAG（人审简版）

## 一句话结论

在同一组 **120 道菜、360 项现实原料** 上，以游戏目录中预先标定的可接受原料 ID 为标准，原始搜索匹配有 **56/120** 道菜的所有原料都对应正确；当前完整 RAG（本地 Top5 召回＋按菜一次 Provider 候选选择／拒匹配）达到 **94/120**。净增 **38 道菜**，配对比较为 38 道改善、0 道退步、82 道不变。这里的“正确”是 **Gold 命中**，不是 JEV 对菜谱合理性的重新评分，也不是线上用户准确率。

## 同集结果

| 指标 | 原始搜索匹配 | 当前完整 RAG | 变化 |
|---|---:|---:|---:|
| 全菜正确：一道菜的每项原料都命中可接受 ID | 56/120（46.7%） | **94/120（78.3%）** | **+38 道／+31.7 个百分点** |
| 单原料正确：该项命中可接受 ID | 264/360（73.3%） | **327/360（90.8%）** | **+63 项／+17.5 个百分点** |
| 不走目录兜底的原料项 | 314/360（87.2%） | **345/360（95.8%）** | **+31 项** |

全菜正确是主指标；“不走兜底”只说明链路找到了一个可映射的候选，**不等于**它选得正确。两侧兜底项分别为 46/360 和 15/360，均保留在全菜及单原料正确率的原始分母中，不删样。每道菜三项原料；菜名互不重复，原料名称允许重复。对照结果的 360 个 `query_id` 一一对应，双方的可接受 ID 集合逐项一致。

## 提升来自哪里

原始链路主要用目录词面搜索，再选排名最高的可用候选；没有合适候选时进入目录兜底。完整 RAG 先用本地 E5 从静态目录召回每项的 Top5，再让当前文本 Provider **按菜一次**判断每项应该选哪个候选 ID，或明确回答“无匹配”。因此它既能从 Top5 中挑出并非排第一的合理原料，也能拒绝貌似相近但实际不合适的原料；无匹配进入目录兜底，核验故障则整菜退回本地 RAG。

作为机制拆分，同一批 Gold 下，中间的“仅本地 RAG”是 **84/120 全菜、318/360 单项**；加上候选选择／拒匹配后为 **94/120、327/360**。因此 **56→94** 是相对原始链路的完整方案提升，**84→94** 是 Provider 选择这一步的净提升，并非重新训练 embedding 或扩大 Top5。本地 RAG→完整 RAG 有 12 道改善、2 道因过度拒匹配而退步；用户已明确接受这一取舍，不能把这两道退步藏在总提升里。

## 代价与适用边界

- 完整 RAG 每道需要映射的新菜最多增加一次文本 Provider 请求。离线 140 次调用（120 道菜＋20 条无对应物挑战）的单次核验耗时中位 **8.32 秒**、P95 **50.48 秒**；这只是新增步骤，不是完整出菜耗时。两次超时及一次无效响应仍按原分母计入，未重试。费用未与服务商账单独立核对。
- 20 条专门构造的无对应物挑战中，完整 RAG **20/20** 正确进入兜底；这是拒匹配能力的单独验证，不混入正常菜准确率的 120 道分母。
- 样本是策划的离线菜品集，不是随机用户流量。离线输入包含双语菜名，生产链路只使用当前可用的菜名；已完成产品代码接入与 fake/回归测试，但**未用真实产品路径重新调用 Provider 或 JEV**。产品默认仍为原始 LEGACY，只有内部显式启用 RAG 时才会走新链路。因此这些数字不应写成正式版已经达到的线上准确率。
- 先前人审简版报告里的“旧 65/120→当时 RAG 92/120”属于**事后翻译歧义修正后的 JEV 合理率**。本报告的“56/120→94/120”属于同集 **Gold ID 命中率**，且右侧增加了 Provider 候选选择；两组数字定义和链路版本不同，不能横向拼接。
